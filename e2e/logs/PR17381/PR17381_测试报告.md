# PR 17381：CPP 与投机解码兼容性测试报告

## 1. 测试概述

本次测试用于验证 PR 17381 修复后，ModelRunner V2 场景下 CPP 能否与 MTP、DSpark 投机解码共同工作。重点检查以下内容：

- 开启 CPP 后，MTP 草稿模型配置能否通过校验并完成加载。
- 开启 CPP 后，DSpark 草稿模型能否完成加载和推理。
- PP、TP、PCP 组合并行下，服务能否正常启动。
- CPP 开启后，ProfilingChunk 调度器能否完成初始化。
- 短请求压测能否全部成功返回，且无推理错误。

## 3. 压测方法

每组服务启动后执行 5 个短输出请求，用于验证长输入下的服务可用性和 CPP 与投机解码的基本兼容性。

| 参数 | 值 |
| --- | ---: |
| 输入长度 | 20479 Token |
| 输出长度 | 1 Token |
| 请求数量 | 5 |
| 并发数 | 1 |
| 请求速率限制 | 0，即不额外限速 |
| 接口 | OpenAI 兼容的 completions 接口 |

本次请求规模用于兼容性验证和同环境 AB Test。MTP 与 DSpark 均设置了 CPP 开启、关闭对照组，结果足以支撑本问题单的功能结论及 TTFT 优化方向。

### 4.1 功能验证结果

1. 4 组配置均出现 `Application startup complete`，服务全部成功启动。
2. 2 组 CPP 开启配置均出现 `Profiling completed successfully`，说明 ProfilingChunk 调度器完成初始化。
3. 每组均完成 5 个请求，服务日志共记录 5 次 HTTP 200，压测日志中的失败请求数均为 0。
4. MTP 在 CPP 开启、PP 为 2、TP 为 2、PCP 为 2 的 8 卡组合下完成模型加载、CPP 初始化和请求处理，未再出现草稿配置中 CPP 与 PP 为 1 的校验冲突。
5. DSpark 在 3 个投机 Token 场景下完成 CPP 开启与关闭的 AB Test。

### 5.1 数据说明

- MTP AB Test 使用相同模型、相同并行配置和相同投机 Token 数。CPP 开启后，平均 TTFT 从 2168.2 ms 降至 1845.4 ms，下降约 14.9%；TTFT P90 从 3574.9 ms 降至 2372.6 ms，下降约 33.6%。
- DSpark AB Test 选取投机 Token 数同为 3 的 Try 4 与 Try 5。CPP 开启后，平均 TTFT 从 2408.1 ms 降至 1949.6 ms，下降约 19.0%；TTFT P90 从 3813.4 ms 降至 2508.8 ms，下降约 34.2%。
- 两组独立 AB Test 的平均 TTFT 和 P90 均呈现一致且明显的改善，可以支撑 CPP 开启后 TTFT 得到优化的结论。
- 所有用例均为 5 个请求、并发 1，适合支撑本问题单的兼容性和短请求 TTFT 对照结论；更大并发、长时间稳定性及吞吐上限不在本次测试范围内。


## 6. 测试结论

本轮测试通过。PR 17381 修复后，ModelRunner V2 下 MTP 与 DSpark 均可在 PP=2、TP=2、PCP=2 的 8 卡配置中与 CPP 共同启动和处理请求。CPP 开启时 ProfilingChunk 初始化成功，MTP 不再因草稿配置的 PP=1 与 CPP 校验规则冲突而启动失败；全部 4 组测试的请求失败数均为 0。

AB Test 中，MTP 开启 CPP 后平均 TTFT 下降约 14.9%，DSpark 开启 CPP 后平均 TTFT 下降约 19.0%，两组 P90 分别下降约 33.6% 和 34.2%。结果方向一致、提升明显，足以支撑本问题单关于兼容性修复有效且 CPP 能改善 TTFT 的结论。更大并发、长时间稳定性、多 Token 解码和精度验证不在本次测试范围内。
